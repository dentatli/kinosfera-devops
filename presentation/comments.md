# Комментарии к презентации

Денис Татлибаев. План выступления на 10 минут.
Тайминг включает короткие паузы на схему и таблицы; проверь темп на репетиции.

## 1. КиноСфера — 0:00–0:40

Я развернул готовый Linux-бинарник bingo как API истории киносеансов.
Основная задача — обеспечить работу сервиса при отказе одного экземпляра
приложения и восстановить этот экземпляр автоматически.

В решении две реплики приложения, PostgreSQL, балансировка, HTTPS, HTTP/3
и мониторинг. Сервис доступен из интернета. Внешний checker прошёл 20 из 20
тестов. Реальную работу QUIC я дополнительно проверил отдельным клиентом
с ноутбука через мобильную сеть.

Дальше покажу путь запроса, обнаруженные проблемы и способы их решения,
затем результаты проверки и автоматизацию установки.

## 2. Требования и границы решения — 0:40–1:30

По заданию отказ одной реплики должен проходить незаметно для клиентов,
а восстановление занимать меньше минуты. При двух работающих репликах
нужны 180 запросов в секунду в течение минуты и стабильные 60 запросов
в секунду. Отдельно проверяются пять профилей при 120 RPS: p90 меньше
400 миллисекунд и не больше одного процента ошибок.

p90 означает, что 90 процентов измеренных задержек не превышают указанное
значение. Ошибки считаются отдельно, поэтому быстрые успешные ответы сами
по себе недостаточны для прохождения проверки.

Сразу обозначу границу решения: все компоненты находятся на одной Ubuntu.
Я обеспечиваю восстановление реплики приложения. Общая PostgreSQL,
физический хост, роутер и домашний интернет остаются точками отказа.

## 3. Архитектура — 1:30–2:50

Покажу запрос слева направо. Клиент обращается к публичному домену.
Роутер направляет TCP 80 и 443, а также UDP 443 на Ubuntu в Hyper-V.

Первым запрос принимает Nginx. Он завершает TLS, обслуживает HTTP/3
и кеширует только long_dummy. Обычные API проходят дальше без кеша.
Следующий компонент — HAProxy. Он распределяет запросы round-robin между
двумя bingo и активно проверяет их здоровье через ping.

Обе реплики используют одну PostgreSQL. Приложение запускается в контейнере
под UID 10001, а не от root. Для каждой реплики установлен лимит памяти
2 ГБ. Внутренние порты приложений, БД и мониторинга не проброшены на роутере.

Nginx отвечает за входной протокол и кеш, HAProxy — за проверки здоровья
и поведение при отказах. Это две разные роли, поэтому я сохранил оба компонента.

Метрики идут отдельным потоком: события запросов из Nginx получает экспортёр,
Prometheus опрашивает его и HAProxy, Grafana показывает графики.

## 4. Бинарник и узкие места — 2:50–4:10

До развёртывания нужно было разобраться с поведением готового бинарника.
Он запрещает запуск от root, использует фиксированный путь конфигурации
и вычисляет порт по student_email. Поэтому порт рассчитывается при установке,
а конфигурация HAProxy формируется с тем же значением.

При старте обнаружился запрос к 8.8.8.8 на TCP-порт 80, который задерживал
инициализацию. Я добавил узкое правило REJECT только для этого направления
из Docker-сети проекта. Оно быстро отклоняет соединение, не подменяя HTTP-ответ.
Правило восстанавливается отдельной systemd-службой.

Другая проблема — запросы к PostgreSQL без нужных индексов. Подготовка данных
создала 29 019 фильмов, 500 тысяч клиентов и 5 миллионов сессий. Для поиска
по id добавлены уникальные индексы, для поисковых полей и связей — обычные.
Затем выполнен VACUUM ANALYZE, чтобы обновить статистику планировщика.

В одиночном SQL-замере поиск по id изменился с 39,567 до 0,082 миллисекунды.
Эти числа показывают эффект индекса, но не являются HTTP-задержкой под нагрузкой.

## 5. Восстановление реплик — 4:10–5:35

Здесь важно разделить обнаружение отказа и восстановление процесса.
HAProxy каждую секунду проверяет ping и исключает нездоровую реплику
из балансировки. Это позволяет направлять новые запросы на оставшийся экземпляр.

Docker healthcheck отмечает состояние контейнера, но сам по себе не перезапускает
живой зависший процесс. Поэтому внутри контейнера работает watchdog:
после трёх неудачных ping он завершает приложение. Docker с политикой
unless-stopped запускает контейнер снова. На старте есть пауза для инициализации.

GET и HEAD допускают ограниченные повторы на другой реплике при ошибках.
Ответы POST и DELETE автоматически не переигрываются: первая попытка могла
уже записать данные, даже если клиент не получил ответ. Для безопасных повторов
записей понадобились бы идемпотентность и поддержка ключей на уровне приложения.

Локально я проверил по очереди обе реплики: завершение процесса и состояние
HTTP 500. Одновременно шло 60 RPS на настоящий db_dummy. Ошибок у клиента
не было. Максимальное восстановление — 0,913 секунды после завершения процесса
и 7,351 секунды при HTTP 500. Внешние crash и OOM-тесты показали около 4,15 секунды.

## 6. Нагрузка — 5:35–6:55

В таблице показаны локальные профили. Генератор задаёт фиксированный поток,
а не просто отправляет следующий запрос после завершения предыдущего.
Ожидание в очереди генератора включается в задержку. Это помогает увидеть
перегрузку вместо искусственно хороших результатов.

Пять профилей шли по 30 секунд при 120 RPS: по 3600 запросов на профиль.
Для operation и db_dummy p90 около 102 миллисекунд, для трёх API по id —
около 1–1,4 миллисекунды. Во всех этих выборках ошибок нет.

Пиковый профиль 180 RPS длился минуту и дал 10 800 запросов.
Стабильный профиль 60 RPS тоже длился минуту. Оба прошли без ошибок.

Локальные и внешние числа я разделяю. Внешний checker задавал цель 200 RPS,
но фактически достиг 182,4 RPS: p90 300,46 миллисекунды, ошибок ноль.
Он отправил 600 запросов, поэтому это короткая внешняя выборка.
Длительный профиль 180 RPS я подтвердил отдельно локальным тестом.

## 7. Дополнительные требования — 6:55–8:05

Сервис доступен по доменному имени через HTTP и HTTPS. HTTP не перенаправляется
на HTTPS, как требует задание. Сертификат самоподписанный, что тоже разрешено
условиями. При проверке клиент явно доверяет именно этому сертификату.

Бонус HTTP/3 в checker проходит по заголовку Alt-Svc. Поэтому я сделал
отдельную проверку настоящего QUIC из мобильной сети, с выключенным Wi-Fi
на телефоне и без VPN. Клиент согласовал h3, получил 200 pong и проверил
сертификат. Перехода на HTTP/2 не было. Проверка заняла 1,375 секунды;
сравнение скорости HTTP/2 и HTTP/3 я не проводил.

Кеш включён только для long_dummy. TTL — 50 секунд, выдача просроченных ответов
отключена. Локальная проверка длилась 65 секунд: 96,825 процента ответов
быстрее секунды, максимальный возраст ответа 50,149 секунды.

Grafana показывает RPS, ошибки, p90 и состояние реплик. Точные доли ошибок
нагрузочного теста беру из отчёта клиента, а не только из графиков.

## 8. Выбор инфраструктуры — 8:05–8:55

Первоначально стенд работал в VirtualBox, где возникали общие паузы ядра
на 25–59 секунд. Они затрагивали сразу обе реплики. Поэтому основной Linux
перенесён в Hyper-V, после чего локальная приёмка прошла.

Затем публичный вход был организован через небольшой VPS и обратный SSH-туннель.
Из отдельных сетей соединения до VPS не доходили. Точный участок проблемы
установить не удалось, поэтому я не называю виновником конкретного оператора.

Итоговая схема — домашний белый IP и прямой проброс портов. После настройки
DNS и HTTPS первый полный прогон дал 19 из 20 из-за одного неполученного ответа.
Повтор без изменения конфигурации прошёл 20 из 20. VPS в итоговом маршруте
не участвует.

## 9. Установка и итог — 8:55–10:00

Код и конфигурации находятся в репозитории. Установка автоматизирована
Ansible: в inventory задаются адрес Ubuntu, домен и email. Контроллер можно
запустить прямо на сервере или использовать SSH с отдельной Linux-машины.

Playbook подготавливает Ubuntu, устанавливает Docker и Compose, включает
синхронизацию времени и доставляет файлы. Затем вызывает install.sh:
тот генерирует конфигурации, создаёт сертификат и запускает сервисы.
Пароли случайные. Данные и индексы готовятся один раз, повторный запуск
сохраняет БД и пароли.

Ansible проверен на действующем стенде: первый прогон без ошибок,
второй — changed=0. Полную установку на совершенно пустой Ubuntu ещё
предстоит проверить, поэтому я отделяю готовую автоматизацию от проверенного
пути установки с нуля.

Итог: внешний checker 20 из 20, реальные нагрузочные и аварийные проверки,
отдельно подтверждён внешний HTTP/3. Для дальнейшего повышения доступности
нужны несколько хостов, резервирование PostgreSQL и входного прокси,
резервные копии с проверкой восстановления и CI/CD.
